# r12 owner hardware test sequence

The r12 image is a test candidate, not an accepted release. Work through these gates in order. Report each gate's pass/fail and the exact screen behavior before moving to the next; a failure in boot, input, network or recovery takes priority over optional features. Do not send passwords, PINs, tokens, OAuth JSON, Bluetooth addresses, full calendar details or unredacted logs.

1. **Flash and first boot.** Preserve the prior personalized card if needed; Raspberry Pi Imager must finish writing and verifying the r12 custom `.img.xz`. With the Pi off, connect HDMI, touch, audio and power. Record whether the Luma welcome screen appears, time to reach it, and any USB overcurrent, display, or boot error. Stop if there is overcurrent or overheating; do not repeatedly reconnect the suspect cable while powered.
2. **Input, network and recovery.** Confirm touch works in all four corners, the system keyboard appears where needed, Wi-Fi lists networks, and Stanford eduroam/Visitor reaches the internet through the approved flow. Set up Pi Connect and verify this computer can reach the Pi before entering Google credentials. Reboot once and verify Wi-Fi and Pi Connect return. If remote terminal access is available, run `sudo -u luma python3 /opt/luma/qualification/device_smoke.py` before enabling Tailscale and report its status only, not private logs.
3. **Core display.** Check time/weather, theme changes, large-type legibility, agenda layout, screen rotation/touch mapping, settings save across reboot, brightness and sleep/wake. Let each animation/game run and cycle away/back; score and state should persist until game loss. Check all themes, including grid alignment in the arcade theme.
4. **Audio and local voice.** Select/test HDMI and HAT speaker outputs; run the three-phrase Hey Luma check, then ask time, weather and next event. Test at 1 m before trying 3 m or background audio. Start a short timer; it must make an audible alarm even while the display is off for Sleep. Check microphone-off really disables responses. Report exact phrases and observed response, but no recordings unless separately agreed.
5. **Google and daily data.** Import the desktop OAuth JSON locally; authorize Calendar and choose agenda, to-do and Sleep calendars. Check busy-day layout, event colors/times, multi-day all-day tasks, completion color syncing in both directions, weather cache, and the start/end of a timed `Sleep` event. Reboot and verify sign-in and selections survive. Do not send the JSON or account credentials.
6. **Phone privacy and commands.** Pair the iPhone, verify nearby presence unlocks private cards and walking away hides them. Reboot with phone absent and confirm privacy remains. Test PIN-protected Forget Device and re-pairing. Enroll Pi Connect if not already done, then Tailscale private HTTPS/Shortcuts and token denial/acceptance. Confirm calls/media stay on the phone and only supported hub commands affect Luma. Do not send command tokens.
7. **USB backup and safe updates.** Insert a known, expendable USB drive and confirm it appears in Luma's inventory; create an encrypted settings backup, remove/reinsert the drive, and verify the backup is discoverable. Do not restore over the live personalized installation without a separate verified copy. Exercise signed update verification/install/rollback only with a purpose-built accepted test release, while Pi Connect remains available; no stable `main` release should be published before owner approval.
8. **Optional device and resilience.** Test Levoit only after its network path and model are confirmed. The optional Pi Wi-Fi sharing AP requires Stanford/network-owner approval and a separate compatible USB Wi-Fi adapter; do not enable it otherwise. Then test offline cache, ordinary reboot and settings persistence. Deliberate power-cut tests come last, only after a recoverable whole-card backup and with synthetic data first.

For each gate, report: **image r12; gate number; pass/fail/blocked; exact action; expected vs observed; any on-screen error; whether it survives reboot.** A photo of an error screen is useful but optional. Stop and report a failed foundational gate before entering more personal data. The complete [hardware acceptance checklist](HARDWARE_VALIDATION.md) remains the release gate; this sequence only orders the owner's first pass.
