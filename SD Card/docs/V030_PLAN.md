# Luma 0.3.0 iPhone remote plan

Status: development, not published. 0.2.11 is already signed, qualified and pushed. This release adds a private, minimal phone window into Luma and remote configuration without changing the wall dashboard or weakening its presence gate.

## Product and setup

Use Safari, optionally installed with Add to Home Screen, through the existing private Tailscale HTTPS hostname. No Mac, native app signing, developer mode or additional carrier app is required. Tailscale on the phone remains required. The mobile interface follows Hearth, Luma Glass and Neon Grid fonts/colors, with thumb-sized controls, concise copy and no games or animation loop. Keep a small static Luma mark.

The hub displays a PIN-protected enrollment QR with a five-minute, single-use ticket in its URL fragment, not query or logs. The phone creates a nonextractable P-256 signing key in IndexedDB and submits its public key. Both screens display a comparison code; the owner approves the matching pending browser with the hub PIN. This one-time approval prevents a stolen/raced QR from silently enrolling someone else. A new QR cancels the prior ticket. Device lists and revocation require the hub PIN. No PIN is stored or sent to the phone.

Install to Home Screen before enrollment if desired, then enroll that window. Safari and Home Screen storage are separate: only cookies, not IndexedDB keys, are copied during installation. A lost/cleared key requires re-enrollment, never an automatic credential export. See [WebKit storage behavior](https://webkit.org/blog/14787/webkit-features-in-safari-17-2/).

## Security boundary

The existing opt-in loopback gateway remains private behind Tailscale Serve. Keep `/command` and its existing token contract unchanged. Add only `/remote/` static assets and a fixed companion API allowlist; never proxy arbitrary local paths, headers, methods, URLs or shell commands. Keep service hardening, bounded requests, no access logs, no public Funnel and no broad CORS. Tailscale identity headers require a loopback-only backend and must not be treated as physical phone attestation. See [Tailscale Serve identity headers](https://tailscale.com/docs/features/tailscale-serve).

Credentials bind a public key, configured private HTTPS origin, Tailscale user identity and the hub's selected phone bond. Browser possession is proved on every private operation with a fresh single-use challenge over the exact method, allowlisted action/path and SHA-256 body digest. Challenges live in bounded RAM, expire after 30 seconds and bind the current Bluetooth authorization generation. Consume before verification; invalid signatures, replay, changed body, wrong identity/origin and old Bluetooth sessions fail closed. Use standard WebCrypto P-256/SHA-256 signatures with the specified raw `r || s` format, converted to DER only for the Python verifier. See [WebCrypto ECDSA](https://www.w3.org/TR/webcrypto/#ecdsa).

Nonextractable browser keys are not Secure Enclave attestation, proof of a physical iPhone, or protection from same-origin malicious script/OS compromise. Enrollment authorizes a particular browser window while the owner confirms it on the hub. Strict CSP, no third-party script, no HTML injection, gateway identity checks, PIN approval and revocation reduce that risk. Do not advertise hardware-bound authentication. Changing the selected phone invalidates existing grants.

Private access requires the selected phone's live **authorized ANCS** session, not pairing, RSSI, a pending Connect, Tailscale reachability, PIN-unlock grace or cached presence. Disconnect, authorization loss, phone change and API restart invalidate pending challenges and in-memory sessions. Recheck before mutation and before returning private results after slow provider requests. An already accepted update can complete safely after disconnect; no second command is accepted. Credentials remain revocable and can survive normal updates, but backups/restores must not silently re-enable old grants.

No private events, tasks, notifications, tokens or settings are cached on the phone or by a service worker. Poll serially while foregrounded, no faster than every five seconds; cancel on background/navigation and erase the preview when hidden, offline, disconnected or authorization fails. Do not promise background Bluetooth synchronization on iOS. Server enforcement is authoritative; the screen can only clear already-rendered contents when Safari runs again. Disable history previews where practical, but do not claim screenshots or suspended-app snapshots can be remotely erased.

## Interface and allowed operations

Three tabs: **Hub** (time/weather, upcoming events, tasks, timer/departure summary), **Settings** (theme, brightness, volume, weather location/timezone, cycle, night, voice controls, calendar selections), and **Software** (current version, check, release review, explicit install, progress and rollback status). Omit private notification bodies and game state. Use explicit data projections, not the full state/settings dump containing phone address or future fields.

Calendar controls reuse all existing saved IDs, default/completed-color semantics, multi-calendar selections, due ordering and ETag protections. Sync now reuses the existing lock and five-minute worker. Expose provider status without raw exceptions/tokens. Do not permit a failed catalog fetch to overwrite selections. Task changes require write consent and an expected ETag; never queue/replay an uncertain write.

Expose only enumerated commands/settings with existing validated types/ranges. Do not expose PIN reset, bond removal, OAuth secret export, token rotation, backup download, arbitrary networking, privileged recovery or root tools. Hub enrollment/revocation remain local. Runtime diagnostics expose safe numeric/status fields only. Settings requiring disruptive reconnect/reboot need clear confirmation rather than disabling the transport beneath an unconfirmed request.

Update review remains signature-verified against the offline key and exact candidate, with a fresh proof for explicit installation. Show progress on the phone; distinguish connection loss from failed update, reacquire after services restart and show final installed/restored version. Reuse the existing protected broker rather than installing from a branch or doing git pull on the Pi. This release does not claim an automatic OS reboot until that separate lifecycle change is implemented and qualified.

## Google from the phone

Existing Desktop OAuth credentials and grants remain untouched. Their localhost callback resolves to the phone when opened there and cannot simply be changed to a Tailscale hostname. Remote calendar management/sync works with the current grant. For actual phone sign-in, implement a separate optional **Web application** OAuth client configured with the exact private HTTPS callback; generate copyable setup instructions on the hub. Never use deprecated out-of-band copy-code sign-in. See [Google client redirect requirements](https://developers.google.com/identity/protocols/oauth2/native-app).

Store the optional web client on the Pi only, accept upload over authenticated HTTPS with bounded JSON, never return its secret. Separate pending state/verifier records from Desktop consent; bind remote state to browser ID, origin and current authorized Bluetooth session, enforce 15-minute expiry and atomic single consumption. Callback may lack proof headers after Google's redirect: valid pending state alone permits only exchange, never API access. Recheck live presence and grant/revocation before exchange and before committing credentials; canceled/expired sign-in retains existing tokens. Return a fixed remote route with no code/state in the visible history; redact callback access logs and set no-store/no-referrer. Use Safari's normal external sign-in, not an embedded webview. Remote task-write consent remains explicit. If exact callback/client setup is absent, show actionable instructions, not a fake success.

## Implementation sequence and acceptance

1. Authentication foundation with storage bounds, PIN approval, revocation, canonical request proofs, nonce replay protection and presence-generation checks. Keep dormant until endpoint/gateway tests pass.
2. Add narrowly scoped companion API projections/actions, split controller operations where necessary so local and remote callers share validation without bypassing authorization. Test both callers and existing `/command` compatibility.
3. Add gateway asset/path allowlist, origin/identity validation, headers/CSP/body budgets and no-cache behavior; preserve disabled-by-default ingress and systemd confinement. No new network listener.
4. Build mobile UI, local hub enrollment UI/QR and optional Home Screen metadata. Foreground-only synchronization and ephemeral private state first; no offline private preview.
5. Implement separate optional Google web-client consent and remote calendar/task management. Validate exchange with synthetic transport tests; owner verifies real consent on Safari.
6. End-to-end browser tests at portrait sizes for all three themes, enrollment/revoke, background/disconnect clear, restore/restart, failed calendar catalog, command/update confirmations and long text. Run crypto interoperability with actual browser-generated nonextractable keys. No source test proves iOS storage, radio or actual Google consent.
7. Full backend/frontend/packaging suites, exact-commit CI, signed 0.2.11→0.3.0 switch/health-failure rollback and service hardening/transport checks. Publish Beta only after software gates pass, with explicit owner hardware acceptance steps.

Release gate: remote enrollment, settings, Google management and update workflow must function together with privacy enforced server-side. A static mobile mockup or authentication-only scaffold is not a completed 0.3.0 release.
