# Luma 0.3.1 implementation and acceptance

Status: active development on `codex/v031-multiuser`; not released. The published release remains 0.3.0. Do not install a partial branch or reset existing bonds/accounts.

## Agreed behavior

One primary and up to four secondary profiles have unique nicknames, one registered iPhone each, isolated Google credentials/calendar selections/tasks and independent timers. Primary approval creates the profile and approves phone/browser enrollment once; the secondary then finishes optional personal setup without the primary remaining nearby. Provide guided, resumable steps for both people. All hub-wide settings, user management and updates are primary-only and PIN-protected, including the primary remote. Secondary personal configuration and timers do not require the primary PIN.

Show all authorized present users in the corner. Calendar/task slides use separate panels for everyone with configured personal information: 1 full-width; 2/3 columns; 4 as 2×2; 5 as three above two. All calendar panels share one interval, whole-hour rulers and exact minute positions, with every overlap represented. Preserve Google colors, task ordering/completion/deadline indicators and theme typography. If present users have no private integrations, keep public standby time/weather/games without showing an absent user's saved data.

Each remote sees only its own account. Secondary remotes are preferred; use individual Tailscale node sharing and HTTPS-only grants, never the primary login or public Funnel. If guest transport is impractical, primary-only remote is an allowed explicit fallback, not a reason to remove multi-user Bluetooth/wall/timer/setup features.

October 8 clarification: the owner explicitly accepts primary-only iPhone remote access if secondary Tailscale sharing proves difficult. Keep secondary remotes preferred for now. Offer a primary-PIN-controlled remote policy rather than changing or deleting secondary profiles. Restriction must revoke secondary browser grants and clear pending enrollment/proof/OAuth attempts; reenabling must require new enrollment, never revive old grants. Secondary users retain wall setup, Google information, Bluetooth presence and timer controls. Local guided personal setup must not depend on guest remote availability.

Use independent live ANCS authorizations, not paired/connecting/RSSI/cached presence. A coordinated per-adapter scan/connect scheduler reconnects registered phones fairly without disturbing healthy sessions or external/manual attempts. One shared advertisement remains active while any eligible phone is absent. Authorization loss immediately redacts that user. Physical validation of five simultaneous links is required before claiming it works on the Pi's radio.

The primary Sleep calendar remains room-wide even when the primary is absent. After 3 stable seconds, show a 5-second themed arrival screen and short cue; after 15 absent seconds, show departure. Hide private data immediately, not after debounce. Coalesce simultaneous arrivals/departures; do not announce restored startup state or replay stale transitions. Suppress transitions/chimes during Sleep, manual off and updating; timer alarms have priority. Personal voice questions require a name/chooser when multiple users are present. The generic wall Timer button and anonymous voice timers remain room timers; each user also has one independent timer accessible from their own remote or the named wall control. Alarms last five seconds and remain audible during Sleep, with private labels redacted for absent owners.

## Implementation order and gates

1. Profile repository and isolated credentials/cache/timers within existing schema 1; retain legacy primary records and rollback compatibility. Test capacity/identity validation, concurrent writes, revocation, restore and isolation.
2. Multi-device BlueZ supervisor, fair shared scheduler/advertisement and per-user authorization generations. Private D-Bus five-device transport tests, failure isolation, incoming/manual connection races, disconnect/subscription-loss/daemon-restart tests.
3. Per-profile Google clients/sync/ETag writes and presence-safe panel projections, room sleep remaining primary-owned. Bound concurrency and stagger five-minute refreshes. Provider failure must affect only its account.
4. Role-aware signed companion requests, primary PIN administration, local/legacy endpoint authorization, personal-only remotes and timers. Guided primary/secondary setup, optional OAuth configuration and privacy consent.
5. Cohesive wall roster/panels, synchronized timeline, announcement/chime arbitration, voice disambiguation and all timer controls. Render all themes and profile counts at 2048×1536 and effective CSS sizes; mobile flows at 320/390px.
6. Full suites, exact-main CI, offline signing, exact deployed 0.3.0 verifier/install/health-failure rollback, production downloaded-asset verification and GitHub Beta publication. Do not reuse a published version's assets.
