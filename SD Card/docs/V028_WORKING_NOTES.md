# 0.2.8 wake protection and iPhone reconnection

Status: [signed 0.2.8 Beta published](https://github.com/BrianBGoldshtein/LumaSmartHub/releases/tag/v0.2.8) from main commit `132abc530b016275a71564204a029433916b8205`, after green main CI and exact-archive qualification. This is not a hardware-accepted fix. The owner reports continued false wakes during ordinary speech and successful manual iPhone connection but no automatic reconnection. Both remain active 0.2.8 acceptance gates. Preserve Google authorization, Wi-Fi, PIN, Bluetooth bonds, voice assets and game state; do not reflash to apply this application update.

## Voice findings and implementation

The live command grammar can force unrelated speech into its limited vocabulary. The independent unrestricted decoder already existed, but releases through 0.2.7 defaulted to the single-decoder mode and required calibration evidence before allowing the stronger filter. Partial constrained guesses also lit the listening orb before a final check. These are code findings, not proof of the exact utterance that triggered the owner's Pi.

0.2.8 defaults to independent corroboration. New wakes must be an exact “Hey Luma” near the start in both final transcripts. Brief hesitation words are allowed, but an unknown-word marker or arbitrary conversation prefix is not. The listener stays visually silent for partial guesses and rejected wakes. Incomplete audio and utterances beyond the nine-second replay limit cannot open or use a command window: comparing full speech with a truncated tail would be invalid. A verified wake alone still opens one seven-second follow-up window; a completed command consumes that window.

Legacy v1 settings, including the old standard default, resolve to the protected mode. An explicit owner-local selection stores v2 `standard` or `dual_decoder`. The more-sensitive escape hatch remains available without a calibration prerequisite, with a clear warning about false activation. It still rejects quoted wakes and incomplete audio. Microphone checks and call trials retain their original acoustic/recall evidence rather than falsely marking a check passed when the default changes. No audio or readable transcript is saved by this fix.

This is not speaker identity. Both recognizers share Vosk's acoustic model; they differ in decoding vocabulary, so their errors are not statistically independent. A real “Hey Luma” spoken by a person on a call can pass both. During a call that actually contains the wake phrase, microphone-off is the reliable immediate control. The existing optional speaker trial remains an experiment; it is not silently enrolled or promoted into live voice authorization.

The shipped Vosk vocabulary contains `luma`, but recognition still depends on pronunciation. A disposable eSpeak synthetic probe produced “they bloom…” for several positive wake examples, which the protected mode would reject. It did not establish usable positive recall. Do not broaden the wake to “they bloom,” “hey Laura,” or arbitrary fuzzy matches to make this probe pass. Use the owner's guided phrase check and a no-wake call test to measure real recall and false activation. `source/tools/probe-wake-decoder.py` reproduces the smoke check; it is explicitly not an accent/room benchmark.

Research alternatives: [openWakeWord](https://github.com/dscripka/openWakeWord) supports VAD and user-specific second-stage verifiers, but it has no supplied Hey Luma model. Training a custom wake needs varied positive audio and substantial negative coverage; renaming a supplied Jarvis detector would not detect Luma. [sherpa-onnx keyword spotting](https://k2-fsa.github.io/sherpa/onnx/kws/index.html) supports custom keywords and is another candidate for a separately qualified acoustic detector. Neither runtime/model is installed or claimed implemented in 0.2.8. A future replacement needs pinned artifacts, license review, ARM64 latency/memory measurements, held-out owner positives and realistic call/TV negatives. It must not change the updater's dependency fingerprint opportunistically or use voice recognition as the phone/PIN privacy key.

## Bluetooth findings and implementation

Code previously used Luma-initiated central scans/connects only. An ANCS notification consumer should also be a BLE peripheral/GATT client, while iOS supplies the GATT service. [TI's ANCS implementation](https://github.com/TexasInstruments/ble-sdk-210-extra/blob/master/Projects/ble/ancs/README.md) describes advertising ANCS service solicitation. [BlueZ LEAdvertisement1](https://github.com/bluez/bluez/blob/master/doc/org.bluez.LEAdvertisement.rst) exposes this as `SolicitUUIDs`. The missing accessory advertisement is a plausible explanation for manual-only reconnect, not a radio trace proving the owner's failure cause.

The API now owns a separate long-lived advertising worker. While the selected paired, bonded, trusted phone is disconnected and its adapter is powered, it exports a connectable `peripheral` advertisement named Luma with the ANCS UUID in `SolicitUUIDs`, NOT `ServiceUUIDs`. No phone address, owner name, account or private information is advertised. It never enables unsolicited pairing or changes discoverability/trust. It unregisters when the selected phone is linked, forgotten, the radio is turned off, or the API stops. BlueZ release/bus loss triggers bounded cleanup and re-registration/retry. A failed registration is visible in Settings and does not prevent the independent connection worker from retrying.

Bounded directed scanning now keeps discovery active during explicit LE Connect; previously discovery stopped immediately beforehand. [BlueZ bluetoothctl documentation](https://github.com/bluez/bluez/blob/master/doc/bluetoothctl.rst) states that an LE connection needs an active scan report. Automatic discovery and explicit connects are still scoped to the saved bond and abort when selection changes. The repair path uses the same in-scan connection behavior. No bond is removed automatically.

An advertisement, RSSI, paired device, or connected link never unlocks private content. Successful authorized ANCS Notification Source subscription remains mandatory. [Apple's ANCS specification](https://developer.apple.com/library/archive/documentation/CoreBluetooth/Reference/AppleNotificationCenterServiceSpecification/Specification/Specification.html) also says the service can appear and disappear; the existing bounded rediscovery/repair remains. No calls or media are routed through Bluetooth.

iPhone-side setup remains Settings → Bluetooth on, with Share System Notifications enabled for Luma. Avoid the Control Center disconnect control when testing proximity reconnect; [Apple documents its accessory-disconnect behavior](https://support.apple.com/en-gb/102412). There is no demonstrated universal iPhone setting that forces any accessory to reconnect from proximity. iOS may still suppress connection, and a notification-accessory solicitation is not a guarantee. Do not instruct the owner to forget/re-pair as a first troubleshooting step: manual authorized ANCS already works.
